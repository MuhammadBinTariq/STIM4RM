# RewardMaxxing v2

This implementation replaces the v1 shell/TRL training path. It preserves the
legacy scripts as research provenance but does not call them. No benchmark
accuracy, speedup, VRAM claim, or memorization reduction has been measured on
Colab yet.

## Entry points

- `src/train.py`: custom on-policy GRPO with real PEFT LoRA adapters.
- `src/rewardmaxxing/policy.py`: batched KV-cached generation, compact rollout
  statistics, and a shared adapter-disabled reference.
- `src/rewardmaxxing/objective.py`: signed group advantages, clipped surrogate,
  additive/sign-corrected multiplicative shaping, categorical forward KL.
- `src/rewardmaxxing/cache.py`: exact-count SQLite WAL cache, cross-thread
  in-flight deduplication, retries, and consistent snapshot/restore.
- `src/rewardmaxxing/stim.py`: token gating, bounded suffix search, boundary
  checks, and tie-aware Spearman correlations.
- `src/evaluate.py`: independent held-out evaluation and paired comparisons.
- `tests/smoke_test.py`: offline CPU tests with tiny random OLMo2 and real PEFT.
- `notebooks/RewardMaxxing_v2.ipynb`: Colab upload/install/pilot/train/evaluate.
- `scripts/colab_run.py`: one arm/seed runner with automatic resume.

## Installation and CPU verification

Use Python 3.11 or 3.12 and an isolated environment. The local smoke test was
executed with Python 3.12, CPU PyTorch 2.6.0, Transformers 4.51.3 and PEFT 0.15.2.

```bash
python -m venv .venv
# Activate .venv using the command appropriate to your shell.
python -m pip install torch==2.6.0 --index-url https://download.pytorch.org/whl/cpu
python -m pip install -r requirements-v2.txt
python tests/smoke_test.py
```

On Linux, the requirements include bitsandbytes for the eventual GPU runner.
The offline test does not load bitsandbytes, datasets, pretrained weights, or an
external API. It tests actual autograd and PEFT, not a fake gradient backend.
Its machine-readable output is `.tmp/smoke-report.json`.

The tests cover tensor shapes, variable-length loss masking, advantage signs,
negative correlation, LoRA-only updates, frozen reference parameters, exact KL,
chunked/dense gradient agreement, generation slicing, checkpoint/optimizer/RNG
resume, API-failure pending-batch recovery without regeneration, cache persistence
and single-flight behavior, failure-vs-zero counts,
answer extraction, overlap calculations, split isolation, and paired statistics.

## Scientific scope and index compatibility

The default model is `allenai/OLMo-2-0425-1B-Instruct`. Its public stage-one corpus
index is `v4_olmo-mix-1124_llama`, indexed with Llama-2 tokenization. That is not
the model's native tokenizer and does not cover all later training stages.
The config therefore explicitly sets:

```json
{
  "mode": "retokenized",
  "acknowledge_proxy": true,
  "corpus_scope": "OLMo-mix-1124 stage-one corpus only; retokenized bounded local proxy"
}
```

This is **STIM-local with retokenization, bounded context and sparse sampling**,
not full-corpus/native-token STIM. All policy candidates are decoded in context,
re-encoded with the index tokenizer, and checked for exact text round trips and
unchanged prefix tokenization. Multi-index-token continuations are counted as
whole sequences, not substituted with a single index token. A single common
context is used for every alternative. Unstable boundaries are excluded and
reported; they are not forced into an arbitrary token mapping.

The strict `native` mode compares vocabulary, segmentation, normalization and
decoder signatures and fails on mismatch. The public index contracts registered
in `build_scorer` do not permit pairing OLMo2 IDs with a Llama index. The native
`v4_dolmasample_olmo` index is associated with the original OLMo tokenizer, not
OLMo2, and still requires corpus/sample provenance qualification. Adding a
private native index requires an explicit registered contract, not a bypass flag.

References:

- [Infini-gram API/index contracts](https://infini-gram.readthedocs.io/en/latest/api.html)
- [OLMo2 1B model and post-training](https://huggingface.co/allenai/OLMo-2-0425-1B-Instruct)
- [Original STIM](https://arxiv.org/abs/2508.02037)
- [VersaPRM adapter and scoring protocol](https://huggingface.co/UW-Madison-Lee-Lab/VersaPRM)

## Objective and rollout semantics

For each prompt, generate G independent responses from the unchanged behavior
policy. Sampling uses temperature 1, top-p 1, top-k disabled. This avoids an
unrecorded temperature/truncation mismatch in the importance ratios. All rewards
and STIM observations complete before an optimizer update.

```
R_i = mean(VersaPRM step scores for response i)
A_i = (R_i - mean_group(R)) / max(std_group(R, unbiased=False), 0.05)
s_it = max(0, Spearman(top-K probabilities, common-context corpus counts))
P_it = gate_it * s_it
additive:       shaped_it = A_i - lambda * P_it
multiplicative: shaped_it = A_i - lambda * abs(A_i) * P_it  (0 <= lambda <= 1)
ratio_it = exp(log_pi_current_it - saved_log_pi_old_it)
loss = mean_valid_tokens(-min(ratio * shaped, clipped_ratio * shaped) + beta * KL)
```

KL is the exact categorical `KL(current || fixed initial policy)` at the sampled
prefixes. Vocabulary projections and loss intermediates are recomputed in chunks
during backward; a full sequence-by-vocabulary tensor is not retained. The
decoder is activation-checkpointed. Every completion token including EOS enters
the task loss; prompt and padding tokens do not. Padding is used for generation
and penalty storage, while each update microbatch uses an unpadded sequence.

There is one optimizer step per fresh rollout batch, not several PPO epochs.
Thus the first-pass importance ratios should be one; clipping is retained in the
objective but is not expected to activate in that configuration. A frozen
behavior snapshot is represented by the saved selected-action log probabilities,
not another model copy. The reference is the fixed base model underneath the new
adapter. A future SFT warm start must become part of that frozen base; disabling
the adapter must not accidentally remove the intended SFT reference.

STIM/gating are detached token-weighted surrogate coefficients. This code does
not claim an unbiased gradient of a fully differentiated sequence memorization
objective. Sparse unselected positions have zero penalty, but are **not** counted
as zero-STIM observations. Raw rho and validity are logged separately.

VersaPRM is frozen and loaded through its documented base-plus-adapter chain.
The runner validates its separator and +/- token IDs. Only the +/- output rows
are projected for step scoring, avoiding vocabulary-sized PRM logits. Quantized
PRM scores require a GPU calibration check before interpreting absolute values.
`reward=outcome` is an explicit separate ablation, never an automatic fallback.

## Scoring budget and cache

Defaults: K=8, at most 4 positions/response, at most 32 index-context tokens,
sampled-token probability >=0.3, context support >=5 and at least 3 distinct
candidate counts. Numeric spans, operators and fixed relation words are eligible.
A small identity whitelist is explicit in `stim.py`; it is not a semantic filter.
Selection favors confidence and distributes positions across newline steps before
filling remaining slots. At most one position per numeric span is selected.

The suffix search is binary over nested index-token suffixes with positive target
count. This is valid because exact substring counts are monotone under suffix
extension. It does not substitute the API's different longest-prefix distribution
semantics for target-dependent STIM context selection.

SQLite stores successful **exact counts**, including true zero, keyed by index,
tokenizer fingerprint, query type, exact IDs and schema. Policy probabilities and
rho are recomputed after updates. Errors and approximate results are never cached
as successful counts. Threads share a cache and deduplicate in-flight requests.
Different OS processes share durable SQLite contents but not in-flight futures.

Keep the live database on `/content`, not a mounted Drive filesystem. SQLite's
backup API creates a consistent snapshot including WAL contents; an atomic file
replace publishes it to Drive. The next session restores the snapshot only into
an empty local cache. Run one experiment process at a time with a shared snapshot
path; concurrent writers to the same Drive snapshot can lose newly cached entries.

Any request failure pauses training by default. A batch with no valid STIM
observations also pauses. Inspect gating/support/boundary statistics on the pilot
before changing the recipe. This intentionally refuses to report a lambda>0 run
that never receives a memorization signal. Performance is not guaranteed by the
public API; use the logged cold/warm timing and coverage measurements.

## Data and experiment protocol

`load_gsm8k` loads only the official `openai/gsm8k` dataset at a pinned revision.
A fixed split seed draws the development set and training subset from the official
training split. Exact normalized question overlap among train/dev/test is rejected.
The split IDs, question hashes and revision are checkpointed.

**Never train using the repository's legacy `data/applied/original.json`.** Its
1,319 questions are the official test questions. v2 never imports that file.

Use three paired seeds, identical model/data revisions and training budgets, and
the same PRM in both arms. Baseline lambda is zero. Select lambda and other
hyperparameters on development data before evaluating test-derived twins. The
512-example default is a feasibility experiment, not a promise of statistical
power or an adequate multi-epoch study.

## Colab execution

See [the execution guide](EXECUTION.md) for Git clone setup, budgets, monitored
pilots, sweeps and separate-process PRM evaluation. The notebook now defaults to
a pinned Git checkout. The ZIP below remains an optional source distribution.

Package the source and open `notebooks/RewardMaxxing_v2.ipynb` in Colab:

```bash
python scripts/package_colab.py
```

The package contains the source needed for an offline upload alternative.
The notebook creates an isolated CUDA 12.4/PyTorch environment and runs the CPU test first.
The default runner requires a BF16-capable GPU with at least 20 GiB VRAM. It stops
on T4/CPU runtimes instead of silently changing precision/rewards/batch sizes.
Actual allocated VRAM is measured by the pilot, not guaranteed by this threshold.

Resolve immutable Hub revisions once and reuse the resolved config for both arms:

```bash
python -m src.prepare --config configs/rewardmaxxing.json --output /content/drive/MyDrive/RewardMaxxing-v2/resolved.json
python scripts/colab_run.py --resolved-config /content/drive/MyDrive/RewardMaxxing-v2/resolved.json --output-root /content/drive/MyDrive/RewardMaxxing-v2 --arm baseline --phase pilot
python scripts/colab_run.py --resolved-config /content/drive/MyDrive/RewardMaxxing-v2/resolved.json --output-root /content/drive/MyDrive/RewardMaxxing-v2 --arm rewardmaxxing --phase pilot
```

Review `pilot-summary.json`, per-step coverage, and runtime. Then use `--phase
train` to continue the same checkpoints. Change `--seed` for paired seed runs.
The configuration is copied to each output directory and the installed dependency
list is recorded. No paid run is launched by building the notebook locally.

## Checkpoints and interruptions

Each checkpoint contains LoRA weights, optimizer and RNG states, the resolved
configuration and data manifest. Only the most recent two checkpoints are kept
by default. Checkpoint paths are published only after writing completes.

Rollouts are saved to `pending.pt` after PRM scoring and before the STIM result is
required. If API scoring fails, the matching policy is checkpointed before exit;
resume reuses the pending on-policy traces and durable successful count queries.
If a hard interruption happened between regular checkpoints, a newer pending
batch is discarded and updates replay from the last saved model/RNG. Newer
old-policy log probabilities are never applied to an older checkpoint.

Use only this run's trusted checkpoint files; optimizer/RNG serialization uses
PyTorch pickle. Direct resume:

```bash
python -m src.train --config path/to/runner-config.json --resume path/to/latest-step-directory
```

The fingerprint rejects changes to model/reward/training semantics. Output/cache
paths, checkpoint retention, and max_steps may change. The Colab runner resolves
the latest checkpoint automatically.

## Evaluation and interpretation

```bash
python -m src.evaluate run --checkpoint path/to/step-000256 --output runs/eval.json --stim-audit --twins path/to/GSM_symbolic.jsonl
python -m src.evaluate run --checkpoint path/to/step-000020 --output runs/dev-step20.json --split dev --limit 32 --stim-audit
python -m src.evaluate compare --baseline runs/baseline-eval.json --rewardmaxxing runs/rm-eval.json --output runs/comparison.json
```

For three seeds, supply three paths to each comparison argument in corresponding
seed order. Comparisons check matching metadata, question IDs, questions and
references. Bootstrap intervals resample seeds and original-problem clusters;
multiple twins are not treated as independent original problems.

`--twins` accepts official GSM-Symbolic JSONL or GSM-Plus JSON/JSONL with
`original_question`/`seed_question` and correct reference answers. It verifies
parent questions against GSM8K test data. Use public twins only in final testing.
Pin and retain the supplied files. Without twins, the output is ID evaluation
only and cannot establish the generalization hypothesis. Structural and numeric
categories remain separate. Raw arbitrary numerical substitution is not supported.

The evaluator reports strict final `#### <answer>` exact match using rational
arithmetic, format failures, length/truncation, PRM step scores, PRM/correctness
correlation, high-PRM wrong answers, exact forward KL at greedy evaluation
prefixes, 4/8-gram training-solution coverage, and maximum training-reference
ROUGE-L F1. ROUGE-L uses documented tokenization and exact bit-parallel LCS,
not approximate candidate retrieval. Similarity to training solutions does not
prove pretraining memorization.

STIM audit sampling is independent of confidence/critical-token training gates,
uses K=20, and logs invalid/missing observations. Sampling is reproducible by
example ID and token position; generated sequences can differ in length, so it is
not a claim that the same semantic tokens are compared. Missing raw STIM values
remain null. Report coverage alongside means and compare an unchanged audit
protocol over checkpoints. Test outcomes must not guide tuning.

## Before interpreting GPU results

The local CPU tests validate mechanics, not the actual pretrained model, API
availability, CUDA kernels, quantized PRM calibration, or tokenizer-boundary
coverage. Run the pilot and inspect its actual measurements. Confirm that lower
STIM accompanies higher paired accuracy without unacceptable ID loss. Do not
equate a reduced STIM surrogate or ROUGE score with proven privacy protection.
